# Project Charter

**Project:** Reliable & Fair Webhook Notifier

**Assignment Duration:** ≤ 15 Days

**Implementation:** Go (Monolith)

**Status:** Completed

---

# 1. Background

F-Company allows customers to register webhook endpoints that receive notifications whenever subscriber-related events occur.

The assignment focuses exclusively on the **Webhook Notifier** component responsible for reliably delivering these notifications to customer endpoints.

To keep the implementation focused, internal event producers and customer webhook receivers may be mocked.

---

# 2. Project Objectives

The implementation aims to:

- Reliably deliver webhook notifications.
- Prevent high-volume customers from starving smaller customers.
- Support horizontal scaling by running multiple notifier instances.
- Recover automatically from transient delivery failures.
- Keep the design simple while remaining extensible.

---

# 3. Assignment Scope

The implementation includes:

- Receiving subscriber events from a mocked producer.
- Persisting webhook delivery jobs.
- Fair scheduling using Round-Robin.
- Concurrent webhook delivery through a configurable worker pool.
- Retrying transient failures using exponential backoff.
- Horizontal scaling through multiple notifier instances.
- Unit tests, integration tests and scheduler benchmarks.
- Architecture documentation and ADRs.

---

# 4. Customer Requirements

The following requirements are derived from the assignment description and customer clarifications.

## Functional

- Deliver webhook notifications for subscriber events.
- Retry failed deliveries.
- Ensure no customer is starved by high-volume customers.
- Support horizontal scalability.
- Treat every HTTP 2xx response as successful delivery.

## Non-functional

- At-least-once delivery is acceptable.
- Event ordering is not required.
- Benchmarks are encouraged.
- Mocking event producers and customer endpoints is acceptable.

---

# 5. Assumptions

The following assumptions were made during implementation.

- Subscriber events already exist before entering the notifier.
- Webhook registrations already exist.
- Customer webhook endpoints are external systems.
- Network failures and HTTP 5xx are considered retryable.
- Other HTTP 4xx responses are treated as permanent failures.

---

# 6. Design Principles

The implementation follows several engineering principles.

## Simplicity

Implement only what is necessary to satisfy the assignment.

Avoid unnecessary distributed components and premature optimization.

## Reliability

Prefer reliable delivery over maximum throughput.

Use persistent storage and retries to minimize message loss.

## Fairness

Ensure every active customer continues making progress regardless of traffic generated by other customers.

## Scalability

Support additional notifier instances without requiring application code changes.

## Maintainability

Favor clear component boundaries, configuration over hard-coded values, and comprehensive automated tests.

---

# 7. Constraints

The implementation intentionally limits its scope.

- Monolithic application.
- Mock event producer.
- Mock webhook receivers.
- PostgreSQL-backed durable delivery queue.
- No Kubernetes dependency.
- Multiple notifier instances simulate horizontal scaling.

---

# 8. Out of Scope

The following capabilities are intentionally excluded.

- Webhook registration APIs.
- User interface.
- Authentication & Authorization.
- Circuit Breaker.
- Dead Letter Queue.
- Replay API.
- Dynamic configuration service.
- Customer SLA tiers.
- Global fairness across multiple notifier instances.

These capabilities could be added without major architectural changes but were considered outside the assignment scope.

---

# 9. Success Criteria

The project is considered successful if it demonstrates:

- Reliable webhook delivery.
- At-least-once delivery semantics.
- Fair scheduling across active customers.
- Automatic retries for transient failures.
- Horizontal scalability by running multiple notifier instances.
- Clean architecture with documented design decisions.
- Automated unit tests, integration tests and benchmarks.

---
