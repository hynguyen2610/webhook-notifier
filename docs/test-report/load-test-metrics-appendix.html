Load Test Metrics Appendix

This appendix explains how the repository records benchmark and load-test-style metrics, what each metric means, and where interpretation can go wrong. It is intended to help reviewers understand what the numbers actually prove before treating them as fairness or scale evidence.

Metric Families

The most important scope rule in this repository is simple: the numbers produced by go run ./cmd/scheduler-benchmark ... are in-memory numbers only. They are useful for component behavior and fairness shape, but they are not PostgreSQL-backed queue measurements.

Benchmark Path What Is Measured What Is Excluded
cmd/scheduler-benchmark in scheduler mode Round-robin scheduler cost, synthetic worker progress, fairness shape under an in-process harness PostgreSQL, notifier HTTP ingest, real webhook delivery, retry and DLQ behavior
cmd/scheduler-benchmark in app mode In-memory notifier flow: enqueue, queue claim, scheduler handoff, worker execution, synthetic completion timing PostgreSQL queue ordering, real outbound HTTP, deployment-level multi-instance contention
scripts/run-multi-instance-benchmark.sh PostgreSQL-backed queue claiming across multiple notifier processes, real worker execution, local mock receiver HTTP delivery Notifier ingest API cost, retries, dead letters, remote network behavior, production infrastructure tuning

How Throughput Metrics Are Recorded

Scheduler Throughput Report

The throughput table in cmd/scheduler-benchmark comes from Go's testing.Benchmark helper and records in-memory numbers only. For each scenario, one benchmark iteration creates a scheduler, enqueues all jobs, drains all scheduled jobs, and shuts the scheduler down.

  • ns/op: average nanoseconds for one full benchmark iteration
  • allocs/op: average heap allocations for one iteration
  • bytes/op: average allocated bytes for one iteration
  • ops/sec: derived as 1 second / ns/op
  • jobs/sec: derived as ops/sec * jobs per iteration

Fairness Run Throughput

The fairness tables use wall-clock timing instead of Go microbenchmark timing, but in cmd/scheduler-benchmark they are still in-memory measurements unless you are using the separate PostgreSQL-backed multi-instance benchmark script. The run starts immediately before work begins and ends when the final job completes.

  • duration: finish timestamp minus start timestamp
  • jobs/sec: total completed jobs divided by duration
Interpretation note: scheduler jobs/sec and multi-instance jobs/sec are not interchangeable. The first is an in-memory synthetic component benchmark. The second is a PostgreSQL-backed processing-path benchmark.

How Fairness Metrics Are Recorded

Metric How It Is Recorded Meaning
first completion Timestamp of the first completed job for a customer minus run start time How quickly that customer begins to make visible progress
finish completion Timestamp of the final completed job for a customer minus run start time How long that customer waits to fully finish its queued work
early completion count How many of the first N completed jobs belong to a customer Whether the customer appears early in the run or is effectively starved at the beginning
early completion share early completion count / early window size The customer's share of the first visible completions

In the current scheduler fairness report, the default early window is the first 20 completions. In smaller scenarios, the window is capped at the total number of jobs in the scenario.

How The Multi-Instance Benchmark Records Results

The PostgreSQL-backed multi-instance benchmark preloads registrations and queue rows into a dedicated benchmark database, launches 1, 2, or 4 notifier processes, and waits until all rows are marked completed.

  • Run start time is recorded from PostgreSQL using clock_timestamp()
  • Completion timing is read from webhook_delivery_queue.completed_at
  • Total throughput is derived from the maximum completion timestamp seen in that run
  • Per-customer progress comes from grouping completed rows by customer_id
  • Early-share values come from the first completed rows ordered by completed_at, id
Why this matters: because the multi-instance benchmark uses real PostgreSQL completion timestamps, it gives stronger evidence about claim order and process contention than the in-memory benchmark does.

How Throughput And Fairness Are Measured In Multi-Instance Runs

In the multi-instance benchmark, the measurement source of truth is the PostgreSQL queue table, not an in-memory benchmark harness. Every notifier instance works against the same webhook_delivery_queue table, and the benchmark reads the final timing data back from PostgreSQL after the run finishes.

Throughput

Throughput answers one question: how quickly did all notifier instances together drain the queued work?

  • The script records the run start timestamp from PostgreSQL with clock_timestamp()
  • Each delivery row is considered finished when its status becomes completed and its completed_at column is set
  • Total duration is measured as the latest completed_at in the run minus the benchmark start time
  • Total jobs/sec is measured as completed row count / total duration

Formula:

Metric Formula
total duration max(completed_at) - benchmark_start_time
jobs/sec count(completed rows) / total duration

Fairness

Fairness answers a different question: as the shared queue drains, do smaller customers start making progress early, or do large customers dominate the beginning of the run?

  • first completion is the earliest completed_at for a customer minus the run start time
  • finish completion is the latest completed_at for a customer minus the run start time
  • early completion share is the fraction of the first N completed rows that belong to a given customer
  • The current benchmark uses N = 20 for that early window

Formula:

Metric Formula
first completion min(completed_at for customer) - benchmark_start_time
finish completion max(completed_at for customer) - benchmark_start_time
early completion share customer rows in first N completions / N
Important interpretation note: a multi-instance run can show better throughput while still showing poor fairness. That usually means the system is draining work faster overall, but PostgreSQL claim order or queue insertion order is still allowing one customer to dominate the early part of the run.

What A Good Or Bad Number Looks Like

  • Good throughput trend: jobs/sec rises as worker count or instance count rises, while total duration falls.
  • Good fairness trend: non-whale customers show early first completions and meaningful early-share presence even when whales dominate the queue.
  • Warning sign: one whale customer owns nearly all of the early-share window.
  • Warning sign: non-whale first completion times cluster close to the end of the run instead of near the beginning.
  • Warning sign: throughput improves but fairness stays poor, which can mean queue claim order is overpowering the scheduler.

Common Interpretation Traps

  • Do not forget that go run ./cmd/scheduler-benchmark --include-large-fairness-case=false records in-memory numbers only.
  • Do not treat scheduler-mode ns/op as production latency. It is a component microbenchmark.
  • Do not compare in-memory app-mode fairness directly against PostgreSQL-backed multi-instance fairness as if they were identical measurements.
  • Do not assume rising throughput means fairness improved. Throughput and fairness can diverge.
  • Do not treat a local mock receiver as proof of real network behavior.
  • Do not ignore insertion order. If queue rows are preloaded in customer-grouped order, claim order can dominate the early part of the run.
